# P2-1 数据持久层 + 预警规则引擎规范

> 本轮即用户所说的「C 业务闭环」（预警规则引擎 / 处置工单流转 / 消息中心），
> 对应路线图中的 P2/P3 合并执行。后续 P2-2 ~ P2-5 同属此轮。

## 1. 背景与问题

当前系统的预警是**死数据**：`server/routes/alerts.js` 直接返回 `mock-data.js` 里写死的 8 条 `alerts`，
没有任何"为什么会产生这条预警"的逻辑，也不会随台风数据变化而变化。

由此带来三个业务断点：

1. **预警不会自动产生** —— 台风强度变了、城市进风圈了，系统毫无反应。
2. **预警没有下游** —— 看到红色预警之后该谁处理、处理到哪一步、有没有闭环，系统里没有任何载体。
3. **处置过程无记录** —— 应急场景最需要"谁在什么时候做了什么"，当前完全没有。

此外，后端每新增一个需要落盘的功能就要重写一遍"读 JSON / 原子写 / 写锁"：
`routes/auth.js` 里已有一份（`readUsers` / `writeUsers` / `withUserWrite`），
照此复制下去会变成和前端 `.warn-*` 一样的"N 份重复"。

## 2. 目标与非目标

**目标**

- 抽出**可复用**的 JSON 持久层，让后续工单、消息模块零重复地落盘。
- 实现**预警规则引擎**：由台风数据 + 城市坐标自动派生预警，可解释（标注命中了哪条规则），可复现（幂等）。
- 预警区分**来源**（规则派生 / 人工发布），避免用户误以为是人工研判结果。

**非目标**

- 不做定时调度 / WebSocket 推送（本轮仍为请求驱动）。
- 不做规则的可视化配置界面（规则以代码常量形式维护，够用且可控）。
- 不引入数据库（保持 JSON 文件存储，与现有架构一致）。

## 3. 设计

### 3.1 持久层：`server/lib/jsonStore.js`

统一解决三件事，供 auth / tickets / notifications 共用：

| 能力 | 说明 |
|---|---|
| `read(file, fallback)` | 文件不存在（ENOENT）或内容为空 → 返回 `fallback`；JSON 解析失败 → 告警并返回 `fallback`（脏数据不得让接口 500） |
| `write(file, data)` | `mkdirSync(recursive)` 保证目录存在 → 写 `.tmp` → `rename` 原子替换 |
| `withLock(fn)` / `mutate(file, fn)` | Promise 链串行化写锁；`mutate` = 读 → `fn(data)` 变换 → 写，**整段在锁内**，避免 read-modify-write 竞态 |

关键点：

- **写锁是全局一条链**（不是按文件分）：本系统数据量极小，一条链换来实现简单与绝对安全；
  多实例部署必须换数据库事务，已在注释中写明这一边界。
- `mutate` 内抛出的业务错误照常向外传播，锁链必须 `then(()=>{}, ()=>{})` 吞掉失败，
  否则一次错误会让后续所有写操作永远挂在 rejected 的链上（这是此类实现的经典陷阱）。

同时把 `routes/auth.js` 里那份私有实现改为复用本模块 —— **这是本步的去重收益**。

### 3.2 地理计算：`server/lib/geo.js`

服务端无法 `require` 前端 `src/utils/geo.js`（那边是 ESM + `import.meta`），
故在服务端镜像一份**同 API** 的实现：`haversineKm` / `nearestApproach` / `ringHit`。

- 口径与前端完全一致：非法输入返回 `null`（绝不用 0 或 NaN 冒充结果），球面距离而非平面近似。
- 已在代码注释标注"与前端 src/utils/geo.js 为同源双份，改一侧必须同步另一侧"。

### 3.3 城市坐标：`server/data/cities.js`

与前端 `src/constants/cities.js` 同源的城市坐标表（含「中国香港/中国澳门」规范名与别名映射）。
服务端需要它才能判断"城市是否在风圈内"——这是规则引擎的输入。

### 3.4 规则引擎：`server/services/alertRules.js`

**纯函数、零 I/O**，因而可单元测试（P2-5 会覆盖）。

输入：单个台风对象 + 城市表；输出：派生预警数组。

规则表（按严重度由高到低，命中即停，避免同一城市被多条规则重复刷屏）：

| 规则 | 条件 | 级别 | 说明 |
|---|---|---|---|
| `RING_12` | 城市到路径最近距离 ≤ `radius12` | red | 12 级风圈命中 |
| `RING_10` | ≤ `radius10` | orange | 10 级风圈命中 |
| `RING_7` | ≤ `radius7` | yellow | 7 级风圈命中 |
| `STRONG_NEAR` | 最近距离 ≤ 300km 且 `windSpeed ≥ 41.5`（台风级） | orange | 强台风逼近但尚未进圈 |
| `WATCH` | 最近距离 ≤ 500km 且 `windSpeed ≥ 24.5`（强热带风暴级） | yellow | 外围关注 |
| `PRESSURE_EXTREME` | 最近距离 ≤ `radius7*1.5` 且 `pressure ≤ 950` | 在命中等级上**上调一级** | 极低压叠加修正 |

补充约定：

- **只对活跃台风派生**（`status === 'active'`）——否则历史台风会刷出一堆过期预警。
- **确定性 ID**：`RULE-<typhoonId>-<city>-<ruleKey>`。幂等是刚需：接口每次实时派生，
  若 ID 随机，前端每次刷新都是"新预警"，工单与通知将永远对不上。
- **可解释**：每条预警带 `source: 'rule'`、`ruleKey`、`ruleLabel`、`reason`（含距离、风速等实际数值）。
- **去重优先级**：同一城市命中多条时只保留最严重的一条，`suppressed: [...]` 记录被抑制的规则，便于排查。

### 3.5 接口改造：`server/routes/alerts.js`

- `GET /api/alerts` —— 返回「人工预警（mock 静态数据）+ 规则派生预警」的合并结果，
  按发布时间倒序；支持 `level` / `source` / `city` / `typhoonId` 筛选。
- `GET /api/alerts/rules` —— 返回规则清单（key / label / 触发条件描述），
  供前端展示"这条预警是怎么来的"。
- 派生结果**不落盘**：ID 确定性 + 输入确定 ⇒ 每次派生结果一致，落盘只会引入"数据陈旧"的新问题。
  工单通过确定性 alertId 关联，不受影响。

## 5. 验收清单

- [ ] 同一台风数据重复调用派生，结果**完全一致**（ID 幂等）。
- [ ] 历史台风不产生派生预警。
- [ ] 城市坐标缺失 / 台风缺经纬度时不报错，该组合跳过。
- [ ] 派生预警带 `source='rule'` 与 `ruleKey`、`reason` 可解释字段。
- [ ] 人工预警仍保留，`source='manual'`，可按来源筛选。
- [ ] `auth.js` 复用 `jsonStore` 后，注册/登录行为不变（P0-2 的并发写锁语义不得回退）。
- [ ] `npm run build` 通过（前端无改动亦须回归）。
