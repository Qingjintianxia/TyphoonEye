# P2-2 处置工单流转规范

## 1. 背景与问题

P2-1 让系统能自动产出预警，但预警到这里就断了——**没有人知道接下来该谁做什么**。

应急场景真正需要的是闭环：预警出现 → 有人认领 → 处置中 → 处置完有结论 → 可回溯。
当前系统里这些环节一个都不存在，预警中心只是"看"的地方。

## 2. 目标与非目标

**目标**

- 预警可一键转为**处置工单**，承载责任人与状态。
- 工单有明确的**状态机**，非法流转直接拒绝（而不是悄悄改掉状态）。
- 每一次状态变更与每一条处置意见都进 **timeline**，可回溯"谁在什么时候做了什么"。
- 提供统计接口，供前端展示各状态数量。

**非目标**

- 不做角色权限（本系统为演示系统，所有登录用户均可操作），但**操作人**必须记录。
- 不做工单附件 / SLA 超时自动升级。
- 不做工单分派工作流引擎。

## 3. 设计

### 3.1 状态机：`server/constants/ticket.js`

单一来源，前端与测试共用同一套语义：

| 状态 | key | 说明 | 可流转到 |
|---|---|---|---|
| 待处置 | `pending` | 已建单未认领 | `processing` |
| 处置中 | `processing` | 已认领在处置 | `pending`（退回）、`closed` |
| 已闭环 | `closed` | 处置完成 | **终态** |

- `canTransition(from, to)` 为纯函数，非法转移返回 `false` 并给出原因。
- `closed` 为终态：不允许再改状态，但**仍可追加处置意见**（复盘补充是真实需求）。

### 3.2 数据模型

工单落 `server/data/tickets.json`，经 `jsonStore.mutate`（读—改—写整段在锁内）：

```
{
  id, alertId, typhoonId, typhoonName, city, level,
  title, description,
  assignee,                 // 负责人用户名，可为空
  status,                   // pending | processing | closed
  createdBy, createdAt, updatedAt,
  timeline: [ { id, at, operator, type, from, to, content } ]
}
```

`timeline` 的 `type`：`create` / `status` / `comment`。

### 3.3 接口：`server/routes/tickets.js`（全部需登录）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/tickets` | 列表；支持 `status` / `assignee` / `level` / `typhoonId` 筛选 |
| GET | `/api/tickets/stats` | 各状态计数 + 逾期/未指派等概览 |
| GET | `/api/tickets/:id` | 详情（含完整 timeline） |
| POST | `/api/tickets` | 从预警建单 |
| PATCH | `/api/tickets/:id/status` | 状态流转，校验合法性 |
| POST | `/api/tickets/:id/comments` | 追加处置意见（closed 也允许） |

业务规则：

- **同一预警不得重复建单**：该 `alertId` 若已存在非 `closed` 工单，直接 400。
  否则用户连点几次就会刷出一堆一模一样的工单——这是此类功能最常见的脏数据来源。
- **操作人取 `req.user.username`**（JWT 解析结果），不由前端传，防止冒名。
- 参数校验失败统一返回 `{code:400, message}`，与既有接口一致。

### 3.4 与消息中心的衔接

C-3 会在本文件的创建/流转/评论处挂上通知钩子，本步先不引入依赖，保持模块边界清晰。

## 5. 验收清单

- [ ] 能从预警建单，必填字段缺失返回 400。
- [ ] 同一预警重复建单被拒（400）。
- [ ] 合法流转成功：`pending → processing → closed`。
- [ ] 非法流转被拒：`pending → closed`、`closed → processing`。
- [ ] `closed` 工单仍可追加处置意见。
- [ ] timeline 完整记录每次操作的操作人与时间。
- [ ] `assignee` / `operator` 来自 JWT，不采信前端传入。
- [ ] 并发建单不丢数据（`jsonStore` 写锁）。
