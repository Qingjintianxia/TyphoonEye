# P2-6 未登录请求噪声治理规范

## 1. 背景

C-5 端到端验证时抓到一类"看不见但确实发生"的缺陷：应用**首屏请求里混着 4 个必然失败的 401**。
它们不影响最终结果（用户不会被卡住），但会带来三个隐性代价：

1. 用户刚打开登录页就弹「登录已过期，请重新登录」——**误报**，且此时根本没登录过；
2. 请求层的 401 全局处理会**清空 token**并把 `unauthorizedHandled` 置位，抑制后续真正的过期处理；
3. 污染监控/日志：401 数量无法再作为"鉴权故障"的信号。

## 2. 根因

CDP 抓取的带时序网络日志（含是否携带 Authorization 头）：

```
[login-page]  401 /api/notifications/unread-count   auth=false
[login-page]  401 /api/typhoons                     auth=false
[login-page]  401 /api/alerts                       auth=false
[login-page]  401 /api/tickets/stats                auth=false
[login-submit]200 /api/auth/login                   auth=false
[login-submit]200 /api/notifications/unread-count   auth=true   ← 登录后正常
```

结论：这 4 个请求发生在**登录页加载阶段**、**未携带 token**，发起者是 `AppLayout` 的 `onMounted`。

为什么登录页会挂载 `AppLayout`？`App.vue` 用 `route.meta.guest` 区分"游客页（登录/注册/404，无侧边栏）"与"受保护页（套 AppLayout）"。
但 vue-router 的**初始路由是异步解析**的：首次渲染时 `route` 仍是 `START_LOCATION`，`meta` 为空对象，
`route.meta.guest` 为 `undefined` → 被判成"受保护页" → `AppLayout` 抢跑挂载 → 发出 4 个无 token 请求。
路由解析完成后切换回 `/login`，`AppLayout` 卸载，但请求已经发出去了。

## 3. 方案

三层防御，缺一不可（前一层是根因，后两层是"再发生也不咬人"）：

| 层 | 位置 | 措施 |
| --- | --- | --- |
| L1 根因 | `src/App.vue` | 路由未解析完成时**不套 AppLayout**（按游客页渲染 `router-view`），从源头消除抢跑 |
| L2 兜底 | `src/components/AppLayout.vue` | `onMounted` 里先判 `isTokenValid()`，无有效 token 直接不发数据请求，只启动时钟等非鉴权逻辑 |
| L3 兜底 | `src/utils/request.js` | 401 且**本次请求本就没带 token** 时：静默抛错，不弹 toast、不清 token、不跳转（登录态交由路由守卫负责） |

设计约束：

- **不改服务端**：服务端拒绝无 token 请求是正确行为，问题在客户端发起时机。
- **不引入"先请求 /me 再拉数据"的串行等待**：那会让首屏多一个 RTT。登录态判断用本地 `isTokenValid()`（JWT exp，含 30s 时钟偏移），零成本。
- L2 只跳过**数据请求**，时钟与事件监听照常，避免布局层出现"半初始化"状态。
- L3 的判定依据是"本次请求是否携带 token"，**不是**"`localStorage` 现在有没有 token"——后者可能在请求飞行途中被并发的 401 处理清空，导致误判。

## 4. 改动清单

1. `src/App.vue`
   - 新增 `routeReady = computed(() => !!route.name)`；
   - `isGuestPage = computed(() => !routeReady.value || !!route.meta.guest)`，即**未就绪按游客页处理**。
2. `src/components/AppLayout.vue`
   - `import { isTokenValid } from '../utils/token'`；
   - `onMounted` 中把 4 个数据请求（`fetchMe` / `fetchTyphoons` / `fetchAlerts` / `fetchStats` + `startPolling`）包在 `if (isTokenValid()) { ... }` 内。
3. `src/utils/request.js`
   - `request()` 内记录 `const hadToken = !!token`；
   - 401 分支：若 `!hadToken`，抛 `ApiError('未登录', { code: 401, status: 401 })` 且不触发 toast / 清 token / 跳转。

## 5. 验收

| 项 | 期望 |
| --- | --- |
| 登录页首屏 | `/api` 请求数为 0（或全部携带 token 且 200） |
| 登录后 | 全部请求 `auth=true` 且 200，无 401 |
| 登录页视觉 | 不出现「登录已过期，请重新登录」 |
| 登录后正常流程 | 工单/消息/预警数据照常加载，未读角标正常 |
| 过期 token 访问内页 | 仍由 401 全局处理清 token + 跳登录（L3 不影响这条路径） |

自动化：`%TEMP%\typhoon_net.mjs`（带时序网络日志）+ `%TEMP%\typhoon_loop_e2e.mjs`（业务闭环全链路）。

## 6. 回归提示

- 该缺陷只在**首屏**出现，手动点几次页面通常复现不了，必须看首屏网络日志——这是本轮引入"带 auth 标记的网络快照"检查的原因。
- 若后续新增"布局层 onMounted 拉数据"，必须同样遵守 L2 的前置判断。
