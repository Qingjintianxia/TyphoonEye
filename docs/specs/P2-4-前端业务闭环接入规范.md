# P2-4 前端业务闭环接入规范

## 1. 背景与问题

P2-1～P2-3 已经把**后端闭环**全部做完：预警能派生、能转工单、工单有状态机、动作会写消息中心。
但前端此刻对这些能力**一无所知**：

- 预警中心只展示预警卡片，看不出这条预警是"人工发布"还是"规则派生"，也没有任何后续动作入口。
- 工单、消息中心两个页面根本不存在，用户拿不到"我该处理什么"。
- 台风详情页与预警是割裂的：详情页看不到该台风产生了哪些预警，更无法就地建单。

一句话：**闭环在服务端是通的，在界面上是断的。**

## 2. 目标与非目标

**目标**

- 新增 `/tickets` 工单中心：列表 + 筛选 + 状态流转 + 处置意见 + 时间线回溯。
- 新增 `/messages` 消息中心：未读/已读、单条已读、全部已读、按类型区分。
- 顶栏消息铃铛带**未读角标**，未读数轻量轮询。
- 预警中心区分预警**来源**（人工发布 / 规则派生），支持**一键生成工单**与**推送通知**。
- 台风详情页展示该台风的关联预警，并可就地建单。

**非目标**

- 不做角色权限（沿用既有约定：所有登录用户均可操作，但操作人必须记录）。
- 不做 WebSocket 实时化（用户已明确暂不需要），未读数采用轻量轮询。
- 不做工单附件、SLA、导出。

## 3. 设计

### 3.1 单一来源：前端常量层

后端 `server/constants/ticket.js` 是 CommonJS，浏览器构建无法直接引用。
因此新增 **ESM 镜像** `src/constants/ticket.js`，与后端**同名同语义**：

| 来源 | 文件 | 消费方 |
|---|---|---|
| 后端（CJS） | `server/constants/ticket.js` | 路由、单测 |
| 前端（ESM） | `src/constants/ticket.js` | 页面、组件、store |

> **约束**：两侧文件头都写明"同源双份，改一侧必须同步另一侧"。
> 前端只做**展示映射**（label/badge/可否流转），不重复实现业务校验——最终裁决权在后端。

新增内容：

```js
TICKET_STATUS = { PENDING: 'pending', PROCESSING: 'processing', CLOSED: 'closed' }
STATUS_META   // { label, badge, order }
ALLOWED_TRANSITIONS // pending→[processing]; processing→[pending, closed]; closed→[]
TIMELINE_TYPES // create | status | comment
statusLabel(status) / statusBadge(status) / statusList() / nextStatuses(status)
ALERT_SOURCES  // { manual: '人工发布', rule: '规则派生' }
```

`nextStatuses()` 是前端禁用按钮的依据：**同一套转移表驱动 UI 禁用态与后端校验**，
避免出现"按钮能点但提交被拒"的割裂体验。

### 3.2 Store 层

`src/stores/ticket.js`

```
state:   tickets, stats, loading, error, submitting, filters{status, level, assignee}
actions: fetchTickets(filters), fetchStats(), createTicket(payload),
         changeStatus(id, status, note), addComment(id, content)
getter:  byAlertId(alertId)  // 卡片上显示"已建单"而不是让用户重复点
```

`src/stores/notification.js`

```
state:   notifications, unread, loading, error
actions: fetchNotifications(), fetchUnreadCount(), markRead(id), markAllRead()
         startPolling(ms=60000) / stopPolling()
```

要点：

- **写操作后必须回写 store 局部状态**（工单更新后原地替换数组项），不要整列表重拉，避免闪烁。
- 未读数轮询放在 `AppLayout` 挂载时启动、卸载时停止；**页面不可见时不轮询**（`document.hidden` 跳过）。
- 消息中心 `markRead` 成功后**同步递减本地 unread**，避免角标要等下一轮轮询才更新。

### 3.4 接口约定（后端已具备，前端仅消费）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/tickets?status&assignee&level&typhoonId` | 列表 |
| GET | `/tickets/stats` | 统计（total / byStatus / unassigned / closedRate） |
| GET | `/tickets/:id` | 详情 |
| POST | `/tickets` | 建单（同一预警已有未闭环工单 → 400） |
| PATCH | `/tickets/:id/status` | 状态流转（非法流转 → 400） |
| POST | `/tickets/:id/comments` | 处置意见（闭环后仍可追加） |
| GET | `/notifications` | 列表（含 read 标记、unread 计数） |
| GET | `/notifications/unread-count` | 角标 |
| PATCH | `/notifications/:id/read` | 单条已读 |
| POST | `/notifications/read-all` | 全部已读 |
| GET | `/alerts/rules` | 规则清单（解释"这条预警怎么来的"） |
| POST | `/alerts/dispatch` | 预警推送（assignee 为空 = 全体广播） |
| GET | `/auth/users` | **新增**，负责人候选 |

### 3.5 交互约定

1. **预警来源可见**：卡片头部加来源 chip（人工发布 / 规则派生），规则派生的在卡片内显示命中的 `ruleKey` 文案。
   理由：自动产出的结论必须让用户知道它是程序算出来的，不能伪装成人工研判。
2. **一键建单**：弹窗预填 `alertId / typhoonId / typhoonName / city / level / title`，用户只补负责人与说明。
   已建单的预警按钮变为"查看工单"并跳转 `/tickets`，避免重复建单报错体验差。
3. **推送通知**：预警中心顶部工具条支持多选预警 → 选负责人（可空=广播）→ 推送。
4. **状态流转**：工单卡片只展示 `nextStatuses(status)` 允许的目标状态按钮；非法目标不渲染，
   而不是渲染出来点了再报错。后端仍独立校验（不信任前端）。
5. **时间线**：工单展开后按时间正序展示 create/status/comment，闭环工单仍可追加意见。

### 3.6 风险与控制

| 风险 | 控制 |
|---|---|
| 前后端状态机不同步 | 常量同源双份 + 文件头互指注释；前端 UI 禁用只是优化，裁决在后端 |
| 未读数轮询打爆接口 | 60s 间隔 + `document.hidden` 跳过 + 单飞（上一轮未结束不发起下一轮） |
| 预警 ID 不稳定导致工单关联丢失 | 依赖 P2-1 的确定性 ID（`RULE-<typhoon>-<city>-<rule>`），已验证幂等 |
| 重复建单 | 前端先查 `byAlertId` 置灰，后端仍返回 400 兜底 |

## 4. 验收标准

- `/tickets` 能列出工单、按状态筛选、完成 `pending→processing→closed` 流转、追加意见、看到时间线。
- 非法流转（如 `pending→closed`）按钮不出现；直接调接口返回 400。
- `/messages` 能看到消息，标记已读后角标数字减少，且**只影响当前用户**。
- 预警中心每条预警有来源标识；一键建单成功后工单中心可见该工单。
- 台风详情页能看到该台风关联预警并可建单。
- `npm run build` 无警告、无错误。
