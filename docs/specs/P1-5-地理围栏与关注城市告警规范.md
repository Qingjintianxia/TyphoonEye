# P1-5 地理围栏与关注城市告警规范

## 1. 背景与问题

P1-4 解决了"单个台风对某个城市的影响评估"，但它仍是**被动**的：用户必须自己选中城市才能看到结论。

应急场景真正需要的是**主动告警**——"我关心的城市一旦进入风圈，系统立刻告诉我"。而当前预警中心的条目全部来自后端静态数据（`server/routes/alerts.js`），没有任何"基于地理位置自动触发"的能力。

## 2. 目标与非目标

**目标**

- 用户可设置**关注城市**，并持久化到本地（刷新后保留）。
- 对**活跃台风**自动计算：关注城市是否落入任一风圈（围栏触发）。
- 触发时在监控页与预警中心给出围栏告警条目，按风圈级别对应预警四色。
- 提供可操作信息：距进入风圈还有多少 km、最近距离时刻。

**非目标**

- 不做服务端推送 / 定时轮询（用户已确认本轮不引入实时化）。
- 不做多用户同步（关注城市存本地 localStorage 即可）。
- 不做短信 / 邮件 / 浏览器通知。

## 3. 设计

### 3.1 关注城市存储：`useWatchedCities`

- 新建 `src/composables/useWatchedCities.js`，持有城市名数组并持久化到 `localStorage`。
- 存储 key：`typhooneye.watchedCities`。
- 读取时做**容错与过滤**：JSON 解析失败、非数组、城市名未在 `cities.js` 收录的条目一律丢弃，避免脏数据导致计算崩溃。
- `localStorage` 不可用（隐私模式 / 配额满）时用 `try/catch` 降级为**纯内存态**，功能仍可用，只是刷新丢失——绝不因存储异常而白屏。
- 默认关注城市为空，由用户自行添加（不做默认城市，避免"替用户决定看哪里"）。

API：`watched`、`isWatched(name)`、`toggle(name)`、`remove(name)`、`clear()`。

### 3.2 围栏判定

**完全复用 P1-4 的 `assessCityImpact()`**，不重复实现距离与风圈逻辑——这是 P1-4 把逻辑放进 `utils/geo.js` 的收益。

判定规则：

- **触发（inside）**：`assessment.ring !== null`，即落入任一风圈。严重度取 `ring.level`（12 级→红、10 级→橙、7 级→黄）。
- **临界（near）**：未入圈，但 `nearestKm <= radius7 * 1.3`，提示"接近风圈"，用蓝色。让用户提前准备，而不是等进了圈才知道。
- **正常（clear）**：其余情况不产生告警条目。

### 3.3 计算范围与性能

- 只对 `status === 'active'` 的台风计算围栏——历史台风不触发（否则会刷出一堆过期告警）。
- 组合数 = 关注城市数 × 活跃台风数，量级很小（通常 < 20），直接全量计算，无需索引或缓存优化。
- 用 `computed` 派生，随 store 数据变化自动重算。

### 3.4 展示位置

- 新建 `src/components/FenceAlerts.vue`：既展示围栏告警，也提供关注城市的添加/移除（chips），入口集中，避免用户找不到设置项。
- `TyphoonMonitor.vue`：在筛选栏下方接入（有告警时醒目展示）。
- `AlertCenter.vue`：新增"地理围栏告警"分区。
- **重要**：不修改 `AppLayout` 侧栏已有的 `alertCount` 角标语义——它来自后端 alerts 数据。围栏告警是前端派生结果，混入会让用户误以为服务端新增了预警。两者在 UI 上分区展示。

### 3.5 空值与边界

- 未设置关注城市 → 不渲染告警列表，展示"添加关注城市"引导，而不是空白卡片。
- 关注城市中若有未收录坐标的 → 在管理区标注，且不参与计算。
- 无活跃台风 → 提示"当前无活跃台风"，不报错。
- 台风坐标缺失 → `assessCityImpact` 返回 null，跳过该组合。
